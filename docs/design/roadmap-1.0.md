# v1.0 진행 계획

- 작성: 2026-10-10 · 기준 판: v0.10.0(Store 게시 완료 2026-09-27)
- 한 줄: **기능은 다 들어왔다. 1.0 은 "보여 주는 모습"과 "약속하는 숫자"를 실물에 맞추는 판이다.**

## 1. 1.0 이 무엇인가

로드맵 ①~④(에이전트 브리지 · 연결 패널과 제어 도구 · 받은 문서함 · 문서 기록)는 v0.10.0 으로 이미 나갔다.
남은 ⑤ "1.0 위생"이 1.0 의 전부다. 새 헤드라인 기능을 더하지 않는다 — 표시 펜(1.1)·캔버스(1.2)는 설계만 끝내
두었고([ADR 0003](decisions/0003-annotation-pens.md) · [ADR 0004](decisions/0004-canvas-document-map.md)),
1.0 에 끼워 넣지 않는다.

**1.0 을 지금 붙이지 않은 이유였던 것들**이 곧 할 일이다.

| 이유 | 지금 상태 | 1.0 에서 |
|---|---|---|
| 스토어 스크린샷이 옛 화면 | 2026-07 촬영 4장(v0.6 이전) | 새 세트 |
| 소개 영상이 옛 화면 | v0.6.8 실화면(2026-08-01) | 재촬영 + 브리지 비트 |
| 리스팅이 정체성을 말하지 않음 | "가볍고 오프라인인 리더 & 에디터" — 에이전트·받은 문서함·기록·RTL 언급 없음 | 첫 문단부터 재작성 |
| 브리지가 실사용 노출을 안 거침 | Store 서명본 핸드셰이크만 확인(2026-09-27) | 실제로 써 본다 |
| 성능을 숫자로 말한 적이 없음 | 예산 없음 · `architecture.md` 에 원칙 한 줄 | 기준선 + 예산 + 프로브 |

그리고 이번에 새로 찾은 것 하나:

- **개인정보 처리방침이 브리지를 모른다** — "앱이 문서를 외부로 전송하지 않는다"는 여전히 참이지만, 사용자가
  연결한 에이전트에게 문서 내용이 *건네지고* 그 에이전트는 온라인일 수 있다. Store 에 걸린 방침이 실물과
  어긋나면 안 된다.

## 2. 작업 단위 (순서대로)

각 단위는 `develop-<slug>` 하나 = 데브로그 하나. 크기는 대략적인 세션 수.

### U1 · `perf-budget` — 성능 예산 (2~3 세션) — ✅ 2026-10-11

> **결과**: [performance.md](performance.md). 재 보니 5천 문서 첫 색인 **132.8 s**(FTS `UNINDEXED` 열로 찾는
> O(N²)) · 흔한 낱말 검색 86 ms → v4 마이그레이션(색인 rowid 짝) + 커밋 묶기 + `ORDER BY rank` 로
> **6.0 s · 8.5 ms**. 워커의 목차용 중복 파싱도 걷어냄. 장치 셋(Rust `perf.rs` · `probe:perf` ·
> `tools/perf-app.mjs`) + 예산 파일 하나. 첫 번들 1.8 MB(마크다운 라이브러리가 워커와 메인에 이중) ·
> 기동 셸 약 1 s 는 **다음 후보**로 남겼다(performance.md §6).

**기준선을 먼저 재고, 예산은 그 위에 정한다.** 숫자 없이 "가볍다"고 써 온 것을 숫자로 바꾼다.

| 항목 | 재는 법 |
|---|---|
| 콜드 기동 — 창 표시 · 첫 미리보기 | 릴리스 exe + CDP `performance` 표식, 5회 중앙값 |
| 유휴 메모리(작업 집합) | 기동 30초 뒤 프로세스 트리 합계(WebView2 자식 포함) |
| 큰 문서 — 1MB · 2만 줄 열기 / 타자 지연 / 미리보기 재렌더 | 픽스처 생성 스크립트 + CDP |
| 다이어그램 갤러리 렌더(21종) | 기존 `probe:mermaid` 에 시간 기록 추가 |
| 워크스페이스 5천 파일 — 첫 색인 / 부팅 재색인 / 전역 검색 응답 | 픽스처 폴더 + Rust 측 시간 로그 |
| 브리지 `search_docs`·`read_section` 응답 | MCP 하네스(기존 실구동 스위트 재사용) |
| 설치 크기 | MSIX · NSIS 바이트(이미 매 릴리스 기록) |

- 산출물: `docs/design/performance.md`(기준선 · 예산 · 재는 법) + **`npm run probe:perf`**(회귀 감시) .
- 기준선에서 튀는 것이 나오면 이 단위에서 고친다. 크면 따로 단위를 뺀다.
- 덤: 표시 펜(1.1)의 "질감 자동 끄기" 기준을 같은 장치로 잴 수 있게 된다.
- 검증 규칙은 늘 하던 대로 — 사용자 DB·프로필은 `video/capture/userdata.ps1` 로 비켜 놓고 원복.

## 3. 순서와 이유

```
U1 perf-budget ──┐
U2 bridge-dogfood ━━━━━━━━━━━━━━━━━━┓ (1주, 겹쳐 진행)
                 └─ U3 privacy-docs ─ U4 listing-v100 ─ U5 video-v100 ─ U6 release-v100
```

- **U1 먼저** — 고칠 것이 나오면 화면·동작이 바뀔 수 있고, 리스팅에 숫자를 쓰려면 그 숫자가 필요하다.
- **U2 는 길게 겹친다** — 실사용은 시간이 걸리는 일이라 다른 단위를 하는 동안 계속 쓴다. 고친 것이 UI 에
  닿으면 촬영 전에 끝낸다.
- **U3 → U4** — 리스팅이 방침을 가리키므로.
- **U4 → U5** — 같은 데모 워크스페이스 · 같은 촬영 세션. 스크린샷이 먼저 확정돼야 영상 컷이 흔들리지 않는다.
- **U6 마지막** — 리스팅·스크린샷·영상을 한 제출에 묶는다.
