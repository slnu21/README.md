# 성능 — 기준선 · 예산 · 재는 법

- 작성: 2026-10-11(v1.0 U1 `perf-budget`) · 기준 기계: Intel i5-9400F(6코어 2.9GHz) · Windows 11 · SSD
- 한 줄: **"가볍다"고 써 온 것을 숫자로 바꿨다. 그리고 재 보니 색인이 154초, 검색이 0.5초였다 — 고쳤다.**

## 1. 원칙

- **예산은 회귀 감시선이지 목표가 아니다.** 기준선의 약 1.5~2배(번들은 약 10%)로 잡아, 누가 느리게
  만들면 프로브가 떨어지게 한다. 단일 원천: [`src/tools/perf-budget.json`](../../src/tools/perf-budget.json)
  — Rust 측정과 프런트 프로브가 같은 파일을 같은 규칙으로 읽는다(`_` 키는 주석, 예산에 있는데 안 잰
  항목은 위반, `_info` 로 끝나는 측정은 예산 밖).
- **숫자는 기계에 매인다.** 다른 기계에서 떨어지면 먼저 기준선을 그 기계에서 다시 재고 판단한다.
  예산을 올릴 때는 이 문서의 기준선 표도 함께 고친다.
- **고친 것만 말한다.** 리스팅·릴노트에 숫자를 쓴다면 이 문서의 숫자만 쓴다(U4).

## 2. 재는 법 — 세 층

| 층 | 명령 | 무엇을 | 언제 |
|---|---|---|---|
| Rust | `cd src/src-tauri; cargo test --release --lib perf::perf_ -- --ignored --nocapture` | 5천 문서 색인·재색인·검색 · 브리지 도구 · v4 판올림 | 색인·검색·DB·MCP 를 건드렸을 때 |
| 프런트 | `cd src; npm run probe:perf` | 번들 크기 · 문서 열기 · 타자 지연 · 재렌더 · 다이어그램 갤러리 | 미리보기·편집기·번들을 건드렸을 때 |
| 실물 | `cd src; node tools/perf-app.mjs [--returning]` | 릴리스 exe 기동 · 유휴 메모리 | 릴리스 때(손으로) |

**Rust**(`src-tauri/src/perf.rs`, 평소 `cargo test` 에는 안 돈다): 임시 폴더에 **진짜 파일 DB** 를 앱과 같은
PRAGMA(WAL)로 만든다 — 색인 비용의 큰 몫이 커밋마다의 fsync 라 메모리 DB 는 그걸 숨긴다. 픽스처도 디스크에
쓴다(5천 문서 · 50 폴더 · 18.5MB · `node_modules` 소음 200개 · 1MB 문서 하나). 낱말 빈도는 **지프 분포**
(§5 함정 1). 결과는 `PERF {json}` 한 줄 + 질의별 `PERF-QUERIES`.

**프런트**(`tools/perf-probe.mjs` + `app/dev/perfProbe.ts`): 다른 프로브와 달리 **프로덕션 빌드**로 잰다 —
Vite build API 로 앱과 하네스를 임시 폴더에 함께 빌드하고 `vite preview` 로 띄워 Edge 헤드리스를 붙인다.
미리보기는 `&worker` 로 **진짜 경로**(워커 렌더 → 정화 → mermaid → iframe)를 탄다(데모 경로는 메인 스레드
즉시 렌더라 비용 모양이 다르다). 디바운스는 0 으로 두어 미리보기 시간이 곧 렌더 경로 비용이다(설정값
200/500/1000ms 는 그 위에 더해질 뿐). 새 프로필로 3회 반복해 항목별 중앙값. 새 의존성 0.

**실물**(`tools/perf-app.mjs`): 릴리스 exe 를 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port`
로 띄워 CDP 로 셸·미리보기를 본다. 문서는 argv 로 넘긴다(파일 연결로 여는 경로 그대로). 메모리는 준비 30초
뒤 프로세스 트리(WebView2 자식 포함) 합. **실사용 데이터는 `video/capture/userdata.ps1` 로 비켜 놓고, 무슨
일이 있어도 되돌린다** — `finally` 만으로는 모자라 `exit` 훅에서도 원복한다(§5 함정 4). 기본은 매 실행 빈
데이터(처음 설치), `--returning` 은 데이터를 남긴다(재방문).

**판올림 리허설**: 스키마를 바꿨으면 실사용 DB 의 **사본**에 돌려 본다(원본 경로는 테스트가 거부한다).

```text
copy %APPDATA%\com.readme.app\md-reader.db* <임시폴더>\      (앱을 끄고 -wal·-shm 까지)
set README_DB_COPY=<임시폴더>\md-reader.db
cargo test --release --lib rehearse -- --ignored --nocapture
```

## 4. 이번에 고친 것

1. **색인 O(N²) — v4 마이그레이션.** `file_index.real_path` 는 FTS5 의 `UNINDEXED` 열이라
   `WHERE real_path = ?` 가 **표 전체를 훑는다**. 파일 하나 색인에 두 번(옛 내용 읽기 · 지우기)이라 문서가
   늘수록 제곱으로 느려졌다. `file_meta` 에 짝의 rowid(`fts_rowid` + UNIQUE 색인)를 적고 거기로 찾는다.
   판올림은 임시 표로 한 번 훑어 채우고(상관 서브쿼리면 판올림 자체가 O(N²)), 짝 없는 색인 행(옛 중복·고아 —
   rowid 로 다시는 닿을 수 없어 검색에 영영 남는다)은 지운다. 같은 픽스처에서 154 s → 37 s.
2. **커밋 묶기.** 자동 커밋이면 파일 하나에 문장 서넛 = WAL fsync 서넛이다. 200개마다 끊어 커밋한다(끝까지
   한 덩어리로 묶으면 그동안 포그라운드 쓰기가 `busy_timeout` 까지 기다린다). 37 s → 5.9 s.
3. **`ORDER BY rank`.** `ORDER BY bm25(file_index)` 는 SQLite 가 정렬하므로 맞은 행 **전부**의 `snippet()` 을
   먼저 만든다(문서를 다시 토큰화). `rank` 는 순서가 같고(기본값이 bm25) FTS5 가 안에서 정렬·LIMIT 해
   `snippet()` 이 LIMIT 개에만 돈다. 두 단계 질의(`rowid IN (…)`)도 해 봤는데 바깥 MATCH 를 rowid 마다 다시
   돌려 더 느렸다.
4. **목차용 중복 파싱.** 워커가 `md.render()` 와 `extractToc()` 을 따로 불러 같은 문서를 두 번 파싱했다.
   `renderWithToc` 가 한 번 파싱한 토큰으로 HTML 과 목차를 함께 만든다(결과는 글자 하나 다르지 않다 — 테스트).

## 5. 함정

1. **픽스처가 숫자를 만든다.** 첫 픽스처는 낱말 36개를 고르게 뽑아 모든 낱말이 문서마다 수십 번 나왔고,
   스니펫 비용이 문서당 9 ms 로 부풀어 "두 낱말 검색 530 ms" 라는 병적인 숫자가 나왔다. 실제 글처럼 지프
   분포로 바꾸자 같은 질의가 8~9 ms 였다. 고치기 전/후는 **같은 픽스처**로 비교한다.
2. **`UNINDEXED` 는 "색인 안 함"이 아니라 "찾을 때 훑음"이다.** FTS5 표에서 그 열로 거르는 질의는 전부
   전체 스캔이다. 경로로 찾을 일이 있으면 일반 표에 짝을 둔다.
3. **끝 표식을 문서마다 다르게.** 100KB·1MB 픽스처가 같은 끝 헤딩을 쓰자 1MB "미리보기 완료"가 직전 문서의
   미리보기에 걸려 60 ms 로 나왔다. 디스크에서 읽은 픽스처는 CRLF 라 편집기 길이 비교가 안 맞았다(앱의
   `readFile` 처럼 LF 로 맞춘다).
4. **Node 는 안 풀리는 약속을 기다리다 `finally` 없이 끝난다.** 실물 검증 스크립트가 그렇게 죽어 실사용
   데이터가 비켜 둔 채로 남았다(곧바로 원복, 손실 없음). 사용자 데이터를 옮기는 스크립트는 **`process.on("exit")`
   에서 동기로 원복**하고, 기다리는 것마다 시간 제한을 건다.

5. **화면 밖 타자는 싸다 — 그리고 고친 버그가 숫자를 나쁘게 만들 수 있다.** 10-11 저녁 재측정에서 타자 지연이
   기준선 25.5 → 30.7 ms 로 늘어 보였다. 같은 시각에 기준선 커밋과 나란히 재고(26.0 대 30.7) 커밋을 반씩 갈라
   들어가니 원인은 06 의 Preview 변경 — 그런데 그건 **회귀가 아니라 버그 수정**이었다. 고치기 전에는 앞 문서 위치가
   따라오며 편집기가 맨 위(1줄)로 끌려가, 가운데 줄 타자가 화면 밖에서 일어났다(미리보기 scrollTop 39). 프로브가
   이제 "친 줄이 화면에 보이는가"를 검사한다 — 옛 Preview 로 돌리면 FAIL 3건이 나는 것을 먼저 봤다.
6. **FTS5 는 SAVEPOINT 마다 쌓아 둔 색인을 내려 쓴다.** 색인 한 파일을 한 덩어리로 묶으려고(U6 실측에서 찾은 검색
   누락) 파일마다 SAVEPOINT 를 걸었더니 5천 문서 첫 색인이 6.4 → 8.8 s, DB 가 49 → 54 MB 가 됐다(켬/끔 번갈아 두 번).
   폴더 색인은 이미 바깥 묶음 트랜잭션 안이라 읽는 쪽에 틈이 안 보이므로, 바깥이 없을 때만 `BEGIN IMMEDIATE` 로
   감싼다(`search.rs` `atomically`) → 6.3 · 5.5 s · 49 MB.
7. **성능 명령의 필터는 `perf::perf_`** — `--lib perf` 는 실사용 DB 사본 경로(`README_DB_COPY`)가 있어야 도는 판올림
   리허설까지 잡아 문서대로 치면 늘 FAIL 1건이 났다.
