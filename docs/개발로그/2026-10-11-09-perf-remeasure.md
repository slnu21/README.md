# 2026-10-11 (09) [v1.0] 성능 재측정(한가할 때) — 기동 효과 확정 · 타자 기준선 착시 · SAVEPOINT 가 색인을 늦춘 것

브랜치 `develop-perf-remeasure` · (02)에서 "한가할 때 다시 잰다"로 남긴 것 + (08)의 수정이 성능에 미친 것.

## 재기 전에 — 실사용 데이터를 안 옮기는 길

`perf-app.mjs` 는 `userdata.ps1` 로 실사용 데이터를 비켜 놓는데, **이 세션 자신의 브리지**(Store 0.10.0)가 실사용 DB 를
잡고 있어 거부될 자리였다. (08)에서 만든 임시 식별자 빌드(`com.readme.updtest`)를 그대로 쓰도록 `--identifier` 를 넣었다
— 데이터가 그 폴더로만 가므로 옮길 것이 없다. **띄우기 전에 exe 안에 그 식별자가 있고 실사용 식별자는 없는지 본다**
(아니면 실사용 폴더에 쓴다 — 실제 exe 로 시험해 거부되는 것을 확인). 측정 뒤 실사용 DB 의 수정 시각이 측정 전 그대로임을 봤다.

- **기동** — CPU 4~27% 에서 v0.10.0 과 지금 main 을 번갈아 두 번(각 3회 중앙값): 셸 980·957 → 941·914 ms, 첫 미리보기
  1,707·1,682 → 1,662·1,632 ms. 렌더러를 첫 번들에서 뺀 효과는 **약 40 ms**(부하 중 잠정치 "약 100 ms"의 절반 아래).
- **`probe:perf`** — 전 항목 PASS(두 번). 100KB·1MB 재렌더는 회차마다 ±100~250 ms 흔들렸다(두 번째에 기준선으로 돌아옴).
- **Rust** — 첫 색인 6.3·5.5 s · 검색 8.6 ms · 브리지 `search_docs` 11.5 ms · DB 49 MB(기준선과 같음, 아래 수정 뒤).

## 숫자가 이상해서 판 것 셋

1. **타자 지연이 25.5 → 30.7 ms, 두 번 다 같은 값.** 잡음 모양이 아니었다. 같은 시각에 기준선 커밋(`ea02d61`)을 꺼내 재니 26.0
   → 실제 차이. 반씩 갈라 들어가 `startup-split` 무죄(25.5) → `open-line`(06) → 편집기 변경 무죄 → **Preview 변경**. 그런데 그
   안에 키마다 더해진 일이 없었다. 스크롤 위치를 찍어 보니 옛 판은 타자 중 **편집기가 1줄, 미리보기 scrollTop 39** — 앞 문서
   위치가 따라오는 버그(06 에서 고친 것)가 편집기를 맨 위로 끌어올려, 가운데 줄 타자가 **화면 밖**에서 일어나고 있었다.
   **회귀가 아니라 기준선이 착시였다.** 프로브에 "친 줄이 화면에 보이는가" 검사를 넣고, 옛 Preview 로 돌려 FAIL 3건을 먼저
   봤다. 타자 예산은 고친 기준선의 1.5배(45 / 60 ms)로 — 규칙(기준선의 1.5~2배)대로다.
2. **첫 색인 6.0 → 11.5 s · DB 49 → 54 MB.** (08)에서 색인 한 파일을 SAVEPOINT 로 감싼 것을 켜고 끄며 번갈아 두 번: 켬 8.8·10.8 s
   / 끔 6.4·7.6 s. FTS5 는 SAVEPOINT 마다 메모리에 모아 둔 색인을 디스크 조각으로 내려 쓴다. 폴더 색인은 이미 바깥 묶음
   트랜잭션 안이라 읽는 쪽에 틈이 안 보이므로 → **바깥 트랜잭션이 없을 때만 `BEGIN IMMEDIATE`**(`atomically`). IMMEDIATE 인
   이유: DEFERRED 로 읽고 나서 쓰기로 올리면 그 사이 다른 연결이 커밋했을 때 `busy_timeout` 을 안 기다리고 바로 BUSY 다.
   재측정 6.3·5.5 s · 49 MB, 공존 실측(08) 다시 누락 0(6,076 + 14,519회). 실패 주입 테스트가 보호막 없이 FAIL 하는 것도 다시 봤다.
3. **문서대로 친 성능 명령이 늘 FAIL 1건** — `--lib perf` 가 사본 경로가 있어야 도는 판올림 리허설까지 잡았다. 필터를
   `perf::perf_` 로(CLAUDE.md · performance.md · perf.rs · 예산 파일).
