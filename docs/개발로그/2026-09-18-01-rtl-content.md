# 2026-09-18 (01) 본문 RTL 지원 — 글 방향 설정(자동/왼→오/오→왼)

브랜치 `develop-rtl-content` · 머지 `89ef04c` · 커밋 `519497a` `d60bafc` · Atlas 프로젝트 #27

## 배경

사용자 피드백: "This app has many good and fantastic capabilities but I want to use it on Fasi
language which does not support RTL." — *Fasi* 는 Farsi(페르시아어)의 오타고, 뜻은 "페르시아어로
쓰고 싶은데 앱이 RTL 을 지원하지 않는다"이다. 저장소에 RTL·bidi 를 다루는 코드가 **0줄**이었다:
미리보기 `PREVIEW_CSS` 는 `text-align:left`·`border-left`·`padding-left` 로 좌우를 물리 속성으로
적고, 편집기는 CodeMirror 기본(LTR 고정), `<html lang>` 은 UI 언어(ko/en)를 그대로 박았다.
글자 모양은 Chromium 이 맞게 그리지만 문단이 왼쪽 정렬되고 마침표·숫자·영단어가 반대편으로 튀는,
"읽을 수는 있는데 쓰기 도구로는 못 쓰는" 상태.

사용자가 언어를 모르는 상태에서 검증 가능한가가 결정 조건이었다 — **가능하다**: 방향은 유니코드
글자 속성(UAX #9)으로 정해지고 실행은 Chromium 이 한다. 우리가 만드는 것은 브라우저가 그렇게
하도록 *놔두는 것*(기준 방향·정렬·좌우 여백)이고, 그건 픽셀로 잰다. 사용자 확인: 전역 설정으로 진행.

## 결정·함정

- **컨테이너는 계산한다** — 브라우저 `dir=auto` 는 dir 을 가진 자식을 서브트리째 건너뛴다. 잎에 auto 를
  달아 두면 부모는 볼 텍스트가 없어 LTR. 루트도 같아서 `buildDoc` 이 HTML 을 훑는다(첫 글자에서 멈춤).
- **렌더러는 설정을 모른다** — 워커 결과가 설정에 안 묶이고, 전환이 `buildDoc` 재조립만으로 즉시. `dir` 은
  UA 표현 힌트라 저자 CSS `direction` 이 이겨 강제 모드가 두 줄. 재개 트리거: 워커 프로토콜에 방향을 넣고
  싶어지면 이 결정을 다시 볼 것(지금은 필요 없다).
- **SVG 글자는 direction 을 무시하지만 래퍼는 아니다** — 처음 주석엔 "라벨이 어긋난다"고 적었다가 프로브가
  통과해 다시 봤다. 어긋나는 건 래퍼의 flex 시작점·스크롤 원점. "어긋날 것이다"는 재기 전엔 적지 않는다.
- **첫 글자 위치는 강제 모드 정렬 기준이 못 된다** — RTL 문단 속 영어 문장은 `E` 가 어느 변에도 없다.
  한 줄짜리 블록의 전체 텍스트 범위로 잰다. `cursorCharLeft` 는 어느 모드든 RTL 묶음 안에서 head 를 늘린다.
- **강한 글자 없는 줄은 위 줄을 따른다** — 첫 스크린샷에서 표 구분 행 `|---|` 이 혼자 왼쪽에 있었다.
- `@lezer/common` 은 직접 의존성이 아니라 `NodeProp.isolate` 대신 노드 이름 비교(새 의존성 0).
- 헤어독 파이썬 `s.replace` 를 assert 없이 썼다가 콜아웃 렌더 치환이 조용히 빠졌다 — 치환은 `assert old in s`.

## 비목표

- 앱 크롬 미러링(사이드바 오른쪽 등) — Windows 앱은 UI 언어가 RTL 일 때만. 페르시아어 UI 번역은 별개 요청.
- 아랍 문자 글꼴 번들(Vazirmatn 등) — 새 의존성 = 확인 게이트. 시스템 글꼴 선택으로 대신.
- 검색의 `ی/ي`·`ک/ك` 접기 — unicode61 한계, 알려진 한계로 문서화.
- **원어민 확인** — 글꼴의 ZWNJ·마크다운 기호 자리 같은 *자연스러움*은 잴 수 없다. 요청한 사용자에게
  사전 빌드를 보여 확인받고, 릴리스 노트에 "베타·피드백 환영"으로 낸다.
