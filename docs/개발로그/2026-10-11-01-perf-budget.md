## 결정·함정

- **`UNINDEXED` 는 "찾을 때 훑음"이다** — FTS5 표에서 그 열로 거르면 전부 전체 스캔. 문서 수에 제곱으로 느려지는
  구조가 v0.2 부터 있었는데 실사용 워크스페이스(269 문서)에서는 안 보였다.
- **두 단계 검색 질의는 오히려 느렸다** — "스니펫은 고른 뒤에"를 `rowid IN (…)` 으로 짰더니 바깥 MATCH 를 rowid
  마다 다시 돌렸다. 질의 모양 여덟 가지를 나란히 재서 `ORDER BY rank` 한 줄이 답인 것을 찾았다.
- **픽스처가 숫자를 만든다** — 낱말 36개 균등 픽스처에서 두 낱말 검색이 530 ms 였는데, 모든 낱말이 문서마다
  수십 번 나와 스니펫이 부푼 병적 사례였다. 지프 분포로 바꾸고 전/후를 같은 픽스처로 다시 쟀다.
- **프로브는 프로덕션 빌드로** — 개발 React 로 재면 타자 지연이 몇 배다. Vite build API 로 앱과 하네스를 함께
  빌드해 `vite preview` 로 띄운다(새 의존성 0).
- **실사용 데이터가 비켜 둔 채 남았다** — 실물 검증 스크립트가 안 풀리는 약속을 기다리다 Node 가 `finally`
  없이 끝났다. 바로 원복했고 DB·WAL 크기·시각을 처음과 대조해 손실이 없음을 확인했다. 커밋하는 `perf-app.mjs`
  는 `process.on("exit")` 에서 동기 원복 + 기다림마다 시간 제한 + 비켜 놓기 확인 전에는 아무것도 안 지운다.
- **기동은 회차 간 ±100~200 ms** — 같은 v0.10.0 을 이어 재니 셸 965 → 1,181 ms. 판끼리 비교는 이어서 잰다.
- 안 고친 것(다음 후보, performance.md §6): 첫 번들 1.8 MB 에 마크다운 라이브러리가 워커와 이중 · 셸 마운트
  약 600 ms · 1MB iframe 배치 1.2 s · 유휴 246 MB(대부분 WebView2).
