# 브리지 실사용 기록 (v1.0 U2)

Store 설치본 `readme-md mcp`(0.10.0, Store 서명)를 Claude Code 사용자 범위에 붙이고, **이 저장소 작업 자체**에 쓴
기록. 1주(2026-10-11 ~ 10-18). 무엇을 적나: 도구를 *실제로 골랐는지* · 결과 모양이 쓸 만했는지 · 오류 문구 ·
스코프에 막힌 경우 · 제어 도구 흐름. 작은 것은 U2 에서 고치고 큰 것은 1.1 후보로 옮긴다(맨 아래 표).

판정 표기: ✅ 쓸 만했다 · ⚠️ 쓰긴 했는데 걸림 · ❌ 못 썼다 · 💡 고칠 거리

## 2026-10-11 ~ 12 (세션 2 — v1.0 출하 자율 진행)

연결: 세션 시작 시 도구 6개가 보였다(`search_docs`·`outline`·`read_section`·`list_workspace`·`place_doc`·
`open_in_app`). 서버 = Store 0.10.0 이라 **`open_in_app` 에 `line` 인자가 아직 없다**(main 에만 있다 — 1.0 에 실림).

| # | 도구 | 왜 골랐나 | 결과 | 판정 |
|---|---|---|---|---|
| 1 | `list_workspace` | 이 저장소 문서가 스코프 안인지 먼저 보려고 | 가상 폴더 4(Atlas·ShotLog·README.md·Pulsar) 밑에 각 저장소 `docs\blog` 만 들어 있다. 이 저장소에서 스코프 안은 **`docs\blog` 하나** | ✅ 모양은 읽기 쉬움 |
| 2 | `outline` | `docs/design/roadmap-1.0.md` 목차 | `워크스페이스 밖 경로입니다: …` | ❌ 스코프 |
| 3 | `search_docs` "브리지 MCP" | 이 저장소에서 브리지 문서 찾기 | 0건 — 스코프 안에 그런 문서가 없다(당연) | ⚠️ 0건과 "스코프 밖"을 구분 못 한다 |
| 4 | `search_docs` "에이전트" | 위 대신 넓게 | 5건(다른 저장소 블로그·데모 워크스페이스). 스니펫에 **`\r\n` 이 그대로** 섞여 나온다 | ⚠️ 💡 |

| 6 | `search_docs` "Store 설치" · `root` = `…\docs\blog` | 범위를 좁혀 다시 | 1건, 같은 글. 스니펫에 또 `\r\n` | ✅ / ⚠️ |
| 7 | `search_docs` "설치" · `root` = `…\md-reader\docs` | 저장소 docs 전체로 넓혀서 | **거부** — 스코프(`docs\blog`)를 품는 상위 폴더인데도 "밖" | ❌ 💡 |

관찰:

- **이 저장소 작업에는 거의 못 쓴다** — 사용자가 워크스페이스에 넣은 것은 저장소마다 `docs\blog` 뿐이고, 설계 문서
  (`docs/design`)·CLAUDE.md 는 스코프 밖이다. 스코프는 설계대로(사람이 고른 폴더만) 동작했다. 결국 이 세션의 문서
  읽기는 대부분 파일 도구(grep·sed)로 했다. → 브리지의 값은 **"사람이 고른 문서 집합"에 대해 묻는 것**이고, 개발
  저장소 탐색은 원래 파일 도구의 일이다. 기대를 그렇게 적는 편이 정직하다.
- 스코프 밖 오류가 **다음 행동을 안 알려 준다** — 에이전트는 "그럼 어떻게?"를 모른다. 💡 오류에 "그 폴더를 워크스페이스에
  넣어 달라고 하거나, 제어 도구가 켜져 있으면 `place_doc` 으로 들이세요" 한 줄.
- 오류 문구가 **한국어뿐**인데 도구 설명(`catalog`)은 영어다. 코드 주석에 "사용자에게 그대로 보이는 오류 문구는 한국어"라는
  결정이 있었다 — 사용자에게 보이는 문구라면 규칙(ko/en)대로 💡 **두 벌**로.
- 상위 폴더 `root`(#7) — 에이전트의 자연스러운 첫수가 막힌다. 💡 스코프를 품는 폴더는 범위로 받고 결과만 거른다.
- `place_doc` 은 쓸 수 있었지만 쓰지 않았다 — 사용자 사이드바를 바꾸는 일이라 이번 작업에서 그럴 이유가 없었다.

### 고친 것(같은 날 · `develop-bridge-dogfood`)

- 스니펫 정리(`clean_snippet` — 센티넬·줄바꿈·연속 공백) · 스코프 밖 오류에 다음 수(`outside_scope`) · 오류 문구 ko/en 두 벌 ·
  `root` 가 스코프를 품는 상위 폴더여도 받음(`Scope::overlaps`, 결과는 여전히 `allows` 로) · README 에 Store 링크(#5 에서 찾은 것).
- **고치다가 하나 더** — 릴리스 exe 를 진짜 MCP 파이프로 돌리니(실사용 DB 사본) 상위 폴더 `root` 가 받아지고도 **0건**이었다.
  `/` 로 준 `root` 를 그대로 LIKE 거친 필터에 넣어 `\` 경로가 하나도 안 걸렸다. 에이전트는 `/` 를 흔히 쓴다 — 이전 판에서도
  `root` 를 `/` 로 주면 늘 0건이었다는 뜻이다. 단위 테스트는 `\` 로만 넣어서 못 잡았다 → 구분자를 맞추고 `/` 경우를 테스트에.
- 실구동 7항목: 고친 판 7/7 · Store 0.10.0 1/7(같은 스크립트, 같은 DB 사본).

### 이 세션의 다른 쓰임(U6 실측 · 성능 재측정)

- 실측·재측정 동안은 브리지를 거의 안 썼다. 읽을 문서(설계·로드맵·CLAUDE.md)가 전부 스코프 밖이었고, 그건 사용자가 고른
  범위대로다. **오히려 브리지가 "실사용 DB 를 잡고 있는 다른 프로세스"로서 작업 방식을 바꿨다** — `userdata.ps1` 이 거부될
  자리라 임시 식별자 빌드로 돌아갔고(`packaging/update-check` · `perf-app --identifier`), 그 덕에 업데이트·성능 측정이
  실사용 데이터를 아예 안 건드리게 됐다. 브리지를 상시 붙여 쓰는 개발자에게는 이 길이 기본값이어야 한다.
- 이 세션의 브리지(Store 0.10.0)는 연결된 채 몇 시간 살았고 오류 0.
